# Вопросы для защиты TrustGate

## Чем TrustGate отличается от ruff, flake8, bandit и semgrep? Покажите цифру.

TrustGate не заменяет эти инструменты - он закрывает их слепую зону, и это
измерено на корпусе из 245 samples (`docs/benchmark.md`):

- на дефект-профиле генеративного кода (hallucinated imports/kwargs, stubs,
  placeholders): recall TrustGate **0.854**, bandit 0.341, semgrep 0.171;
- на классических CWE-уязвимостях: TrustGate 0.14, bandit/semgrep 0.28-0.29 -
  здесь сильнее они, и это говорится прямо;
- по общему F1 среди инструментов с FPR < 5%: TrustGate 0.467 - лучший
  (bandit 0.455, semgrep 0.417, ruff 0.346); flake8 дает recall 0.80, но
  помечает 35% чистых production-файлов - как gate непригоден.

Правильная формула на защите: "TrustGate + bandit/semgrep вместе покрывают
оба профиля риска; по отдельности каждый слеп на чужом классе дефектов".

## Где здесь LLM, если инструмент не определяет автора кода?

TrustGate не детектирует "кто писал" - он таргетирует **профиль дефектов**,
характерный для генеративного кода. 5 из 13 детекторов (D01, D02, D09, D13,
D14) построены под этот профиль; ablation показывает, что они дают около
половины recall. Отчет разбивает findings на `llm_specific` /
`general_quality`, а бенчмарк подтверждает: именно на этом профиле baseline
инструменты слепы.

## Кто писал бенчмарк и можно ли ему верить?

Корпус из четырех источников с полным provenance у каждого sample:

1. SecurityEval (MSR 2022, DOI 10.1145/3549035.3561184) - код, реально
   сгенерированный GitHub Copilot; внешний рецензируемый датасет.
2. LLM-решения 23 задач (claude-haiku, claude-sonnet), размеченные
   автоматическим прогоном reference-тестов, а не вручную.
3. Инъекции дефектов в реальный LLM-код - единственный синтетический срез,
   детерминирован по seed, помечен в provenance.
4. Clean OSS-файлы из requests/flask/fastapi, пиненные на release-теги -
   независимая проба false positives.

Smoke-бенчмарк (14 кейсов) остается только регрессионной проверкой механики -
исследовательские выводы делаются на внешнем корпусе.

## Почему это информационная система для 09.03.02?

TrustGate обрабатывает поток данных в процессе разработки:

1. Источник: git-репозиторий или PR-diff.
2. Обработка: AST-детекторы, dependency manifest scan, optional project tests,
   single-file sandbox, mutation testing.
3. Решение: `PASS`, `REVIEW`, `BLOCK`.
4. Представление: Markdown, JSON, HTML, SARIF.
5. Интеграция: CLI и GitHub Action.

Это не только алгоритм, а небольшой quality-gate в CI/CD.

## Почему project scan не всегда запускает тесты?

По умолчанию `scan` безопасно выполняет статическую часть. Для доверенного CI
есть параметр:

```bash
trustgate scan . --project-tests "python -m pytest -q"
```

Это осознанный компромисс. Автоматически запускать произвольные команды из
чужого репозитория опасно; команда тестов должна быть задана владельцем CI.

Если же project tests или mutation layer не запускались, partial analysis не
должен превращаться в PASS: в таком режиме результат сознательно понижается до
REVIEW.

## Почему Trust Score не является математическим доказательством?

Trust Score - это объяснимый risk score, а не доказательство корректности. Его
задача - приоритизировать review и блокировать явно рискованные патчи. Пороги
вердикта откалиброваны на корпусе (`experiment/calibrate.py`): правило "один
critical finding = BLOCK" имеет precision 1.0 и FPR 0 на clean-группе, а
старое правило "3 критикала" не срабатывало никогда - см.
`docs/scoring_rationale.md` с таблицей "до/после".

## Как проверяется эффективность?

Три уровня, все воспроизводимы из репозитория:

- `experiment/static_benchmark.py` - регрессионный smoke benchmark детекторов
  (14 версионированных кейсов);
- `experiment/benchmark_external.py` - внешний корпус 245 samples, сравнение с
  ruff/flake8/bandit/semgrep, per-slice recall, ablation, FP-анализ; результат
  закоммичен в `experiment/benchmark-result.json`;
- `experiment/calibrate.py` - калибровка порогов вердикта на том же корпусе.

## Как подтверждается авторство?

Код разбит на небольшие модули, каждый можно объяснить:

- `detectors.py` - обход AST и правила;
- `scan.py` - git/project workflow, manifest scan, SARIF;
- `sandbox.py` - Docker runner;
- `mutation.py` - генерация AST-мутантов;
- `scoring.py` - агрегация штрафов.

На защите нужно уметь вручную объяснить путь: Python-файл -> AST -> findings ->
penalties -> verdict.

## Самые честные ограничения

- Полная динамическая проверка проекта зависит от явно заданной команды
  `--project-tests`.
- Project tests и project mutation выполняются в изолированной временной копии
  репозитория, чтобы не трогать исходное дерево.
- Mutation testing пока полноценно реализован как ограниченный repository-level
  smoke-check, а не как полный исследовательский корпус-мутатор.
- Python - единственный поддерживаемый язык.
- Детекторы эвристические, поэтому возможны false positives и suppressions.

Эти ограничения не надо скрывать. Их надо показывать как roadmap.
