# Вопросы для защиты TrustGate

## Чем TrustGate отличается от ruff, flake8, bandit и semgrep?

TrustGate не заменяет эти инструменты. Он добавляет слой проверки доверия к
AI-generated патчу. Основной фокус - дефекты, которые выглядят правдоподобно:
выдуманные импорты, похожие на настоящие API, опасные quick fixes, заглушки и
тесты, которые ничего не доказывают.

На защите важно говорить не "TrustGate лучше всех", а точнее: "TrustGate
закрывает отдельный профиль риска и может работать рядом с обычными
линтерами".

## Почему это информационная система для 09.03.02?

TrustGate обрабатывает поток данных в процессе разработки:

1. Источник: git-репозиторий или PR-diff.
2. Обработка: AST-детекторы, dependency manifest scan, optional project tests,
   single-file sandbox, mutation testing.
3. Решение: `PASS`, `REVIEW`, `BLOCK`.
4. Представление: Markdown, JSON, HTML, SARIF.
5. Интеграция: CLI и GitHub Action.

Это не только алгоритм, а небольшой quality-gate в CI/CD.

## Почему project scan не всегда запускает тесты?

По умолчанию `scan` безопасно выполняет статическую часть. Для доверенного CI
есть параметр:

```bash
trustgate scan . --project-tests "python -m pytest -q"
```

Это осознанный компромисс. Автоматически запускать произвольные команды из
чужого репозитория опасно; команда тестов должна быть задана владельцем CI.

## Почему Trust Score не является математическим доказательством?

Trust Score - это объяснимый risk score, а не доказательство корректности. Его
задача - приоритизировать review и блокировать явно рискованные патчи.
Штрафы вынесены в `weights.toml`, чтобы их можно было калибровать на корпусе.

## Как проверяется эффективность?

В репозитории есть два уровня:

- `experiment/static_benchmark_cases.json` - маленький версионированный smoke
  benchmark для регрессионной проверки детекторов.
- `experiment/` - harness для большего корпуса LLM-решений и сравнения с
  `flake8+bandit`.

Честная позиция: текущий smoke benchmark доказывает воспроизводимость базовых
примеров; большой корпус нужен для окончательных исследовательских цифр.

## Как подтверждается авторство?

Код разбит на небольшие модули, каждый можно объяснить:

- `detectors.py` - обход AST и правила;
- `scan.py` - git/project workflow, manifest scan, SARIF;
- `sandbox.py` - Docker runner;
- `mutation.py` - генерация AST-мутантов;
- `scoring.py` - агрегация штрафов.

На защите нужно уметь вручную объяснить путь: Python-файл -> AST -> findings ->
penalties -> verdict.

## Самые честные ограничения

- Полная динамическая проверка проекта зависит от явно заданной команды
  `--project-tests`.
- Mutation testing пока полноценно реализован для single-file scenario.
- Python - единственный поддерживаемый язык.
- Детекторы эвристические, поэтому возможны false positives и suppressions.

Эти ограничения не надо скрывать. Их надо показывать как roadmap.
