# TrustGate Defense Q&A

## How does TrustGate differ from ruff, flake8, bandit and semgrep? Show a number.

TrustGate does not replace these tools - it covers their blind spot, and that
is measured on a corpus of 245 samples (`docs/benchmark.md`):

- on the generated-code defect profile (hallucinated imports/kwargs, stubs,
  placeholders): TrustGate recall **0.854**, bandit 0.341, semgrep 0.171;
- on classic CWE vulnerabilities: TrustGate 0.20, bandit/semgrep 0.28-0.29 -
  here they are stronger, and that is stated directly;
- on overall F1 among tools with FPR < 5%: TrustGate 0.526 is the best
  (bandit 0.455, semgrep 0.417, ruff 0.346), with zero false positives on the
  clean group; flake8 reaches recall 0.80 but flags 35% of clean production
  files - unusable as a gate.

The right formulation: "TrustGate + bandit/semgrep together cover both risk
profiles; separately each is blind to the other's defect class."

## Where is the LLM here, if the tool does not identify the code's author?

TrustGate does not detect "who wrote it" - it targets the **defect profile**
typical of generated code. 5 of the 14 detectors (D01, D02, D09, D13, D14) are
built for that profile; the ablation shows they contribute about half of the
recall. The report splits findings into `llm_specific` / `general_quality`, and
the benchmark confirms it: it is exactly on this profile that the baseline
tools are blind.

## Who wrote the benchmark and can it be trusted?

The corpus comes from four sources, each sample carrying full provenance:

1. SecurityEval (MSR 2022, DOI 10.1145/3549035.3561184) - code actually
   generated by GitHub Copilot; an external peer-reviewed dataset.
2. LLM solutions to 23 tasks (claude-haiku, claude-sonnet), labeled by an
   automatic run of reference tests rather than by hand.
3. Defect injections into real LLM code - the only synthetic slice, seeded
   deterministically and marked in the provenance.
4. Clean OSS files from requests/flask/fastapi, pinned to release tags - an
   independent false positive probe.

The smoke benchmark (14 cases) remains only a regression check of the
mechanics - research conclusions are drawn on the external corpus.

## Why is this an information system rather than just a script?

TrustGate processes a data flow inside the development process:

1. Source: a git repository or a PR diff.
2. Processing: AST detectors, dependency manifest scan, optional project tests,
   single-file sandbox, mutation testing.
3. Decision: `PASS`, `REVIEW`, `BLOCK`.
4. Presentation: Markdown, JSON, HTML, SARIF.
5. Integration: a CLI and a GitHub Action.

That is not just an algorithm, but a small quality gate in CI/CD.

## Why does the project scan not always run the tests?

By default `scan` safely performs the static part. For trusted CI there is a
parameter:

```bash
trustgate scan . --project-tests "python -m pytest -q"
```

This is a deliberate trade-off. Automatically running arbitrary commands from
someone else's repository is dangerous; the test command must be defined by the
CI owner.

And if the project tests or the mutation layer did not run, a partial analysis
must not turn into a PASS: in that mode the result is deliberately downgraded to
REVIEW.

## Why is the Trust Score not a mathematical proof?

The Trust Score is an explainable risk score, not a proof of correctness. Its
job is to prioritize review and block clearly risky patches. The verdict
thresholds are calibrated on the corpus (`experiment/calibrate.py`): the rule
"one critical finding = BLOCK" has precision 1.0 and FPR 0 on the clean group,
while the old "3 criticals" rule never fired - see `docs/scoring_rationale.md`
with the before/after table.

## How is effectiveness verified?

Three levels, all reproducible from the repository:

- `experiment/static_benchmark.py` - a regression smoke benchmark of the
  detectors (15 versioned cases);
- `experiment/benchmark_external.py` - the external corpus of 245 samples,
  comparison against ruff/flake8/bandit/semgrep, per-slice recall, ablation, FP
  analysis; the result is committed in `experiment/benchmark-result.json`;
- `experiment/calibrate.py` - calibration of the verdict thresholds on the same
  corpus.

## How is authorship substantiated?

The code is split into small modules, each of which can be explained:

- `detectors.py` - the AST traversal and the rules;
- `scan.py` - the git/project workflow, manifest scan, SARIF;
- `sandbox.py` - the Docker runner;
- `mutation.py` - AST mutant generation;
- `scoring.py` - penalty aggregation.

One should be able to explain the path by hand: Python file -> AST -> findings
-> penalties -> verdict.

## The most honest limitations

- A full dynamic check of a project depends on an explicitly provided
  `--project-tests` command.
- Project tests and project mutation are executed in an isolated temporary copy
  of the repository so the source tree is left untouched.
- Mutation testing is so far fully implemented as a limited repository-level
  smoke check, not as a complete research-grade corpus mutator.
- Python is the only supported language.
- The detectors are heuristic, so false positives and suppressions are possible.

These limitations should not be hidden. They should be presented as a roadmap.
